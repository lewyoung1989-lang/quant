# 当日尾盘调仓计划：需求与实施交接

整理日期：2026-10-10。项目：quant。技术栈：Python + Streamlit。

本文交接给下一位 AI 实施。先阅读当前代码与适用的 AGENTS.md，再按本文开发。本文不是已上线功能，也不是经过分钟行情回测验证的交易建议。

## 1. 用户已确认的需求

- 同时支持盘中动态判断，以及收盘后生成下一交易日计划。
- 用户填写实际持仓，系统根据实际持仓与策略目标生成调仓清单。
- 在北京时间 **14:45–14:50** 生成可供当日执行的尾盘交易计划。
- 第一版围绕 **创业板 ETF（sz159915）+ 红利低波 ETF（sh512890）** 的轮动策略实施，保留标的与周期参数配置能力。
- 页面需要回答：是否需要操作、买卖什么、预计数量、何时执行、判断原因、数据是否有效。

用户没有要求自动下单、连接券商账户或发送通知。第一版采用手工确认成交、手工更新实际持仓。

## 2. 第一版建议默认值与边界

以下是实施建议，不是用户逐项确认的参数；应放入配置并在界面说明，禁止伪装成已验证的最优设置。

| 项目 | 建议默认值 |
|---|---|
| 时区 | Asia/Shanghai |
| 策略周期 | 20 个交易日 |
| 目标配置 | 满足进攻条件时目标为创业板 ETF，否则目标为红利低波 ETF |
| 决策窗口 | 14:45:00 至 14:50:00 |
| 正式快照 | 14:50 附近第一次通过全部校验的快照；窗口内持续展示预览 |
| 盘中刷新 | 30 秒，可按接口限额调整 |
| 行情最大年龄 | 60 秒，可配置，以行情时间而非请求完成时间计算 |
| 两标的行情最大时间差 | 30 秒，可配置 |
| 正式计划生成宽限 | 14:50:00 至 14:50:30；超过后不自动补发当天正式计划 |
| 标的目标权重 | 默认单一目标 100%，扣除费用与配置的资金预留后计算数量 |

不要引入“连续三次确认”“动量缓冲带”等新交易规则作为隐藏默认值。如增加这些规则，须单独配置、记录版本并重新验证。

“固定计划”指不可变的决策记录，不代表报价一直有效。实际执行前仍需刷新报价和校验持仓；旧价格不能被标记成当前可成交价格。

## 3. 页面与交互流程

新增独立入口“每日信号”，与现有回测功能并列。无需先完成全区间回测才能查看最新信号。

### 3.1 策略与模式

顶部提供保存策略选择、策略参数摘要及两个模式：

1. **盘中监控 / 当日尾盘计划**：展示当前预览，进入 14:45–14:50 后展示决策窗口进度，正式生成后展示当日固定计划。
2. **收盘确认 / 次日计划**：完整收盘数据校验通过后计算确认信号，执行日期为交易日历中的下一交易日。

支持历史日期只读查询。历史查询不应触发当前日期的新计划或持仓变更。

### 3.2 首屏信息顺序

1. 结论：买入 / 调仓 / 继续持有 / 目标需调整但当前受阻 / 暂无法判断。
2. 信号类型：盘中预览、当日尾盘固定计划、收盘确认；类型使用文字标注，不只依赖颜色。
3. 执行日期、行情时间、生成时间、数据来源及有效性。
4. 实际持仓与目标持仓的差异，以及逐项买卖清单。
5. 判断依据：动量、均线、阈值、通过或未通过状态。
6. 可展开的当天信号变化记录、历史计划及关联行情图。

只在目标变化、正式计划生成、失败或需要用户处理时突出提示。连续刷新且信号不变时，不重复弹窗或重复写入同一变化事件。

按钮：立即刷新、保存策略、保存持仓、查看固定计划、记录成交、导出计划。所有按钮文案必须与实际行为一致，不出现“买入”按钮实际上只刷新页面的情况。

### 3.3 实际持仓输入

- 标的代码、持有数量、当前可卖数量。
- 可用资金、持仓更新时间。
- 手动成交记录：买卖方向、实际成交数量、实际成交价格、实际费用、成交时间。
- 保存时验证数值非负、可卖数量不大于持有数量；具体交易单位通过标的规则校验。

持仓持久保存，页面重启后恢复。不能仅保存在 Streamlit session_state，也不能在生成计划时自动假设已成交。

未填写持仓时，可以显示策略目标，但必须提示“无法生成数量清单”。允许用户明确录入空仓及可用资金，这与未填写账户信息不同。

成交记录需支持部分成交与多次成交，按实际成交更新持仓与资金。持仓变化后原计划的账户快照不再有效，剩余清单需重新核对；不能重复使用原完整卖出数量。

## 4. 策略计算口径

当前策略条件取自 strategies/twin_innovation_bond_rotation.py，第一版保持条件一致：

```text
进攻动量 > 0
且进攻价格 > 进攻均线
且进攻动量 > 防守动量
=> 目标为进攻标的
否则 => 目标为防守标的
```

设今天为交易日 t，实时价格为 P(t, now)，周期为 N：

```text
盘中 N 日动量 = P(t, now) / Close(t-N) - 1
盘中 N 日均线 = [Close(t-N+1) + ... + Close(t-1) + P(t, now)] / N
```

两个标的分别计算动量。均线条件只检查进攻标的。严格大于条件不应擅自改成大于等于。

需要至少 N 个此前已完成交易日的数据。今天的动态日线不能再次作为历史数据计入，避免把今日价格重复使用。日期按真实交易日序列定位，不按自然日减 N 天。

历史与实时报价必须使用一致价格口径。不得将前复权历史收盘价与未经转换的实时报价直接混用；分红、复权因子变化或来源不明时应先校验。计算保留精度，界面四舍五入不能改变信号判断。

收盘确认使用完整的当日收盘数据替代实时价格，保留独立记录，不覆盖当日尾盘快照。以交易所交易状态与数据完成标记判断收盘数据是否完整，不要在到达某个时刻后立即假设日线已完成。

若盘中信号与收盘信号不同，显示变化及依据。次日计划仍需对实际成交后的持仓重新比较，不能假设当日计划已经执行。

## 5. 行情与运行先决条件

### 5.1 行情接口

历史日线每日更新，实时行情独立获取，不共享 24 小时缓存策略。

标准化实时报价至少包含：标的代码、最新成交价、行情时间、采集时间、来源、交易状态。若要展示可成交性或限价估算，还需要相应买卖报价、价格限制等字段；缺少这些字段不能宣称订单一定能成交。

使用具有明确接口文档、标的覆盖、访问权限与限额的数据源。实际接入前验证 159915、512890 的行情覆盖、延迟、字段单位和时间语义。任何需要用户账户或付费权限的接口，使用环境配置，不能写死凭据或假装已经开通。

行情质量门禁至少检查：

- 行情日期与当前交易日一致；时间戳合理且没有未来时间。
- 所需两标的都有有效正价格、足够历史数据和可识别的价格口径。
- 年龄与两标的时间差未超过配置阈值。
- 当前是有效交易时段，区分正常交易、休市、暂停交易与接口异常。
- 历史数据不包含晚于信号时点的记录，不使用后来的收盘价补填尾盘价格。

任何失败都输出具体原因并阻止生成可执行清单。可以展示带时间的上次有效信号，但必须标记过期，不允许静默回退到旧行情并显示“实时”。

### 5.2 调度与后台运行

使用上海与深圳适用的交易日历，不只检查星期一到星期五。周末、节假日与特殊休市不生成当天正式计划。

要实现每天自动生成，必须有独立后台进程或系统调度，不能依靠用户打开 Streamlit 页面。页面读取后台保存的状态；手动刷新也调用同一计算与校验服务。

建议提供可独立执行的命令行入口及本地运行说明，并明确“进程运行时才会自动执行”。电脑睡眠、程序关闭或网络断开不应被隐藏。

生成键至少包含策略版本、交易日、计划类型与账户标识。使用原子写入、事务或锁，防止多次刷新、多个进程或重启导致重复生成。

若宽限时间结束仍没有有效快照，记录“当日计划生成失败”；之后只允许显式手动生成带实际时间的补充版本，不得伪造为 14:50 计划。

## 6. 从目标持仓到调仓清单

将“策略目标”“与实际持仓的差异”“当前执行限制”分别建模，不要用一个布尔值表达“能否操作”。

| 场景 | 页面结论 |
|---|---|
| 实际持仓已经满足目标且无数量调整需要 | 继续持有 |
| 已明确为空仓且资金足够 | 买入目标标的 |
| 当前持有另一标的且可卖 | 卖出原标的，再买入目标标的 |
| 需要卖出但可卖数量不足 | 目标需调整，但存在卖出限制；展示可卖和受阻数量 |
| 可用资金不足或不足最小交易单位 | 无法完成目标买入；显示资金缺口或剩余现金 |
| 数据无效或账户信息缺失 | 暂无法判断 / 无法生成数量清单 |

数量估算考虑标的交易单位、资金预留、买卖费用、最低佣金（如适用）与配置的价格缓冲。交易规则按标的维护，不要假设所有 ETF 的可卖限制一致。

卖出未成交前，其预计所得不能作为“已可用资金”。买入清单明确区分：当前资金可执行数量、依赖卖出成交后的预计数量。禁止把卖出被阻止的计划展示为可立即全额买入。

对多个实际持仓或不属于该策略的标的，先明确策略归属。默认不自动卖出用户其他持仓；若策略范围无法确定，要求用户划定参与该策略的持仓和资金。

行情决定的只是估算数量，不保证成交。正式计划固定目标和初始估算；执行前更新报价或持仓造成数量变化时生成新版本并关联原计划，保留审计记录。

## 7. 数据结构与持久化

建议使用 SQLite 保存结构化状态，或采用具有原子写入和文件锁的本地格式。UI 与后台共享同一服务层。

建议实体：

- StrategyConfig：策略 ID、版本、两个标的、N、时区、窗口、刷新和数据门禁阈值、费用与数量规则。
- PositionSnapshot：账户 ID、策略资金范围、持仓、可卖数量、现金、更新时间、版本。
- QuoteSnapshot：两标的价格和时间、历史数据版本、价格口径、采集结果和校验结果。
- SignalResult：策略版本、计算时点、目标标的、各条件数值、信号类型、有效性和原因。
- RebalancePlan：计划 ID、交易日、执行日期、关联快照、目标与差异、订单估算、依赖条件、状态、前版本 ID。
- ExecutionRecord：用户确认的实际成交、费用、时间、幂等记录 ID、关联计划。

状态示例：预览、已固定待执行、受阻、部分执行、已完成、过期、已被新版本替代。数据错误是独立字段，不要将“无数据”误记为防守信号。

运行数据库、账户持仓、行情快照和成交记录不得提交 Git。实施时为选择的本地运行目录补充 .gitignore，并提供不含个人信息的示例配置。源码、迁移和文档可以提交。

| data/etf_pool.py | 标的代码与名称映射 |
| strategies/trade_visualizer.py | 交易流水从收益报告重建，当前与收益引擎成交日期有错位 |
| reports/twin_bond_report.csv | 已保存的历史回测结果；禁止把最后一行直接当当天信号 |

建议模块边界：历史数据服务、实时行情适配器、纯信号计算、调仓规划、持久化、调度、页面。文件名可按项目习惯调整，不要把所有新逻辑塞入 app.py。

审计发现：

1. 原引擎以 t 日完整收盘价生成信号，并假设在 t 日同一收盘价完成调仓；t 到 t+1 的收益记录在 t+1 日期。
2. 交易流水却使用报告日期的收盘价作为买卖价，使买卖时点、单笔盈亏和胜率与引擎不一致。
3. 费用在轮动引擎中硬编码，页面费率输入没有传入；尚未模拟滑点。
4. 缺少行情来源、价格口径、参数版本和运行元信息。

现有 20 日回测：2019-03-26 至 2026-10-09，累计 256.90%、年化 18.38%、最大回撤 27.36%。次日开盘成本情景年化约 17.18%。这些是日线审计结果，**不能作为 14:50 执行的验证结果**。

本地审计文件位于 reports/strategy_audit/，该目录被 Git 忽略，其他机器未必有。实施者应自行检查当前代码，不依赖这些文件必然存在。

## 9. 尾盘回测与验证要求

必须明确区分功能交付与策略收益验证。

- 若验证尾盘策略，使用真实历史分钟或更细行情，14:50 判断只能使用截至该时刻已知的数据。
- 采用分钟数据时明确时间戳是区间起点还是终点；不能使用覆盖 14:50 之后的完整分钟柱生成 14:50 信号。
- 信号出现后才能执行订单，不得用信号计算价格无条件保证成交。配置延迟、费用、滑点和成交约束。
- 不从最终日线收盘反推 14:50 的价格，也不把次日开盘模拟包装为尾盘回测。
- 参数先固定再做验证，保存每次试验配置与结果；历史时间分段若已参与选择，不称为严格样本外。
- 无分钟数据时，交付行情接入和计划功能，并清楚标记“尾盘策略尚未完成历史验证”。

## 10. 必须覆盖的验收场景

### 信号计算

- 手工构造行情，分别验证三个进攻条件全部成立、各条件失败、阈值恰好相等、历史不足。
- 20 日动量与均线索引正确，今日不重复计入，未来数据截断前后相同历史信号不变。
- 缺失或非正价格、未知复权口径不输出有效交易信号。

### 数据、时间与调度

- 一个标的过期、两标的时间差超限、接口断开：阻止正式计划，展示明确原因。
- 非交易日不生成计划；盘中普通时段只出预览；窗口内有预览；14:50 通过校验后只生成一次正式计划。
- 重启、重复点击、后台与页面同时计算，不重复创建同一正式计划。
- 宽限时间后才恢复数据：不得回填伪造的 14:50 时间。
- 页面关闭但后台正常运行，仍能按时保存计划；后台停止时页面可识别最后运行时间与错过的窗口。
- 收盘确认使用完整数据，写入独立记录并显示下一真实交易日。

### 持仓与数量

- 未填账户、明确空仓、已满足目标、需要全额调仓、部分可卖、资金不足、最小交易单位不足。
- 卖出受阻时不把预计卖款计入现有可用现金。
- 费用与预留使买入预算不超额；实际持仓中的其他策略资产不被自动卖出。
- 部分成交、重复提交成交记录、持仓更新后旧计划失效、刷新页面后状态恢复。

### UI 与交付

- 首屏能明确看到动作、执行日期、信号类型、行情时间、依据和限制。
- 历史查询只读，不改变实际持仓和当天计划。
- 现有回测功能继续可用；新功能不依赖原 CSV 的最后一行。
- 使用模拟行情与时钟即可复现上述场景，自动测试不依赖当天真实交易时段。
- 文档包含安装依赖、行情配置、后台启动/停止、日志位置和本地存储说明。
- 提供示例截图与一次模拟生成、部分成交、收盘复核的完整演示。

## 11. 给实施 AI 的执行顺序

1. 检查代码与现有依赖，核验可接入行情接口，明确所需权限与价格口径。
2. 提取纯信号计算，并编写必要的因果性和边界测试。
3. 实现持仓存储、调仓数量与受阻状态、实际成交更新。
4. 实现实时报价、交易日历和质量门禁，再接入每日信号页面。
5. 实现独立后台调度、正式计划幂等生成和收盘复核。
6. 用模拟行情和可注入时钟完成验收；有分钟历史数据再做尾盘回测。
7. 汇报具体改动、通过的检查、运行方式，以及未解决的真实数据/验证限制。

缺少实时数据访问权限时，先完成适配器、模拟验收和其余模块；真实行情状态应显示未配置。禁止把示例行情或旧缓存伪装成实时数据。不要未经授权自动下单、分享账户数据、发布网站或更改仓库公开权限。
